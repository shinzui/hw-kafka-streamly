# 0.1.0.0 Jitsurei live-validation transcripts

Date: 2026-04-17
ExecPlan: docs/plans/5-jitsurei-hardening-and-validation.md

This document records an end-to-end run of every executable in the
`hw-kafka-streamly-jitsurei` cookbook against a local Redpanda broker
started via the repository's `process-compose.yaml`. Each section captures
the invocation, the observed output, and a brief note confirming the
example behaved as its banner claims.

The `librdkafka` IPv6 connection-refused log lines that appear before each
run are normal: `localhost` resolves to both `::1` and `127.0.0.1`, the
IPv6 attempt fails, and librdkafka falls back to IPv4 without user impact.
They are elided below for readability.


## Environment

- Redpanda: rpk v26.1.5 (darwin/arm64), broker `localhost:9092`.
- GHC 9.12.2, cabal-install 3.16.1.0.
- Broker harness: `just process-up` (runs `process-compose up` with
  `rpk container start -n 1 --kafka-ports 9092`).
- Topics: `jitsurei-topic` and `jitsurei-streamly-output`, each
  single-partition, created freshly via `just create-topic` and
  `just create-output-topic` immediately before the run.

All seven executables exited with code 0.

## 3. error-handling

Command:

    cabal run error-handling

Expected: three back-to-back patterns against `jitsurei-topic`, each
with its own consumer group so every pattern sees all 5 records from
offset 0:

1. `skipNonFatal` — silently drops poll timeouts, yields 5 records.
2. `skipNonFatalExcept [isPollTimeout]` — yields the 5 records and
   would emit `Left` for timeouts (here `take 5` finishes first).
3. `throwLeft` wrapped in a `catch` — yields the 5 records; no fatal
   error raised.

The topic was re-primed with a second `streamly-producer` run before
this test (so 10 records exist), but each pattern uses `take 5` and
starts from offset 0 in a fresh group.

Observed (trimmed):

## Conclusion

All seven executables in `hw-kafka-streamly-jitsurei` function as their
banners and documentation claim when run against a local Redpanda
broker on `localhost:9092`. The `ConsumeProduce.hs` fix (replacing the
silent `mapMaybe (either (const Nothing) Just)` with `throwLeft`) did
not change the success path — the transcript is identical to what the
buggy version would have printed for the happy case, but fatal errors
now surface as exceptions rather than being silently swallowed.

This closes the "Validate examples against running Redpanda (manual
test)" checkbox in
`docs/plans/1-streamly-bindings-for-hw-kafka-client.md`.
